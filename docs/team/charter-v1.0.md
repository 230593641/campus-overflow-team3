## 一、团队价值观

1. **代码 reviewed 才合并**：不自己合自己的 PR，至少一个队友看过并打 LGTM。
2. **测试不删不放宽**：红测试是规格说明，不是要消灭的噪音。删测试等于改需求。
3. **有问题当天说**：卡住超过 2 小时就在群里喊，不憋着硬扛。
4. **小步提交**：一个 commit 只做一件事，出问题能回滚。
5. **文档跟着代码走**：改了接口/架构，顺手更新 docs，不留过期文档。

## 三、开发规约

### 分支命名
- 新功能：`feature/<拼音>-<功能简述>`，例：`feature/kong-hello`
- 修 bug：`fix/<问题简述>`
- 文档：`docs/<内容>`
- **禁止直推 main**，所有改动走 PR。

### Commit 格式
```
<type>: <描述>
```
type 用：feat / fix / docs / test / refactor / chore

例：`feat: Question 聚合 post 方法实现`
例：`test: 补 QuestionTest 边界用例`

### 代码要求
- 新功能必须带单元测试，本任务涉及模块的测试全绿才能提 PR
- 不改动已有测试的断言（除非和 PO 确认过测试本身错了）
- 领域层零框架依赖（ArchUnit 会检查）
- 前端不写 `any` 类型，CI 会查

### PR 要求
- PR 描述写清：做了什么、为什么、怎么测的
- 至少 1 人 review + LGTM
- CI 全绿
- SM 负责合并

---

## 四、DoD（Definition of Done）

一个任务算"完成"，必须同时满足：

- [ ] 代码已合并到 main 分支
- [ ] 本任务涉及模块测试全绿
- [ ] CI（GitHub Actions）全绿
- [ ] 新功能有对应单元测试
- [ ] 代码至少被 1 人 review 过
- [ ] 文档/注释需要更新的已更新
- [ ] 看板上的卡片从 In Review 拖到 Done
