# 团队章程 v1.0

> 本章程由 PO 起草、全员 review 通过后生效；修改需全员同意并升版本号。

## 1. 团队名称与一句话愿景

- 团队名称：CampusOverflow 团队 3
- 一句话愿景：让校园里的技术问题，在本校就能被问出来、答清楚、被记住。

## 2. 价值观（每条都是一句可执行的话）

1. **代码 reviewed 才合并**：不做"自己合自己"，PR 至少 1 人 LGTM。
2. **有问题群里说，不憋着**：卡住超过 4 小时必须 @SM，不许闷头死磕。
3. **测试是需求，不改断言**：不删测试、不为绿而放宽已有断言。
4. **承诺了就做到，做不到提前说**：Sprint 承诺故事到期未完成，要在站会上说明并回退。
5. **文档和代码一起交付**：没有文档的完成不算完成。

## 3. 角色与职责边界

| 角色 | 职责 | 不做什么 |
| --- | --- | --- |
| PO（产品负责人） | 需求、Backlog 优先级、验收标准 | 不兼任 SM，不直接分配编码任务 |
| SM（Scrum Master） | 流程、看板、站会、移除阻塞 | 不决定需求优先级 |
| Dev（开发） | 实现任务、写测试、提 PR | 不直推 main |
| QA（由 Dev 兼任，每 Sprint 轮换） | 评审清单执行、环境验证 | — |

角色每 Sprint 末投票轮换，记录见 [角色与分工](角色与分工.md) 末尾"角色轮换历史"。

## 4. 沟通约定

- IM 群：【待填：群名称/二维码位置】
- 每日站会：时间【待填】，形式【待填：文字群/语音】，由 SM 主持，每人三句话（昨天做了啥 / 今天要做啥 / 有啥卡住）。
- PR 响应时效：提出后 24 小时内必须有人 review 或评论；作者 24 小时内处理意见。
- 卡住升级：同一问题卡住超过 4 小时，在 Issue 评论并 @SM；SM 30 分钟内响应，仍无解升级 PO。
- 会议纪要：每次会议 24 小时内归档到 [会议纪要](会议纪要/)。

## 5. 开发规约

- 分支命名：`feature/<issue编号>-<描述>`、`fix/<issue编号>-<描述>`，禁止直推 main。
- commit message：`type(scope): 描述`（feat/fix/docs/test/chore），见 [CONTRIBUTING](../../CONTRIBUTING.md)。
- 测试要求：新功能必须带测试；`mvn test` 指定模块全绿才能提 PR。
- 代码风格：后端遵循现有框架风格；前端走 ESLint + Prettier（S2 第一周补齐）。
- 合并方式：只用 Squash merge。

## 6. 冲突解决机制

1. 技术分歧：先各自陈述依据，由架构负责人拍板，必要时写 ADR；
2. 需求分歧：PO 最终决定，反对意见记入会议纪要；
3. 人际/分工冲突：SM 调解，调解无效由全员投票，票数平交由老师仲裁。
