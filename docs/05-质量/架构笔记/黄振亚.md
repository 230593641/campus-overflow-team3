## 一、Identity 参考实现：五层是怎么落地的

Identity 是课程给的"完整实现范例"，我把它当作整个仓库的**架构标尺**来读。它没有把 46 个文件平铺，而是切成
`api / domain / application / infrastructure / interfaces` 五个 Maven 模块，每层一个独立 jar。读完之后我认为
真正决定架构质量的**不是分层目录本身，而是三个"接口放哪"的决策**。

### 1. 领域层是纯 Java，零框架依赖

`co-identity-domain` 里最核心的 `User` 是一个普通 Java 类：私有 final 字段、构造器私有、静态工厂方法
`register` / `createStaff` / `reconstitute`、行为方法 `verify` / `changeRole` / `disable`。
它**不 import 任何 Spring 或 JPA 的东西**——这一点在 `User.java` 里能直接验证：import 只有
`java.time.Instant`、`java.util.Objects`、`java.util.regex.Pattern` 和共享内核的四个类。

这个选择的收益是立刻可感的：`UserTest` 跑完只要 0.023 秒，**不需要数据库、不需要 Spring 容器**。
领域规则（学号 4–20 位字母数字、昵称 2–20 字且不含 @ 和空格、邮箱格式）全部集中在聚合内部，
由 `Guard.requireText` 统一做前置条件检查，错误码（ID-1001 / ID-1002 / ID-1003）跟业务规则写在同一处。

我特别留意到 `reconstitute` 这个方法：它**刻意不做任何业务校验**，注释写得很直白——"由持久化层重建聚合，
不做业务校验"。业务校验只发生在 `register` / `createStaff` 这两个"新建物"入口。
这和 `save()` 里 `assignId` 回填主键的设计是一套：**领域对象自己管自己的不变量，持久化只负责搬运**。

### 2. 仓储接口在领域层，实现在基础设施层

`UserRepository` 是领域层定义的端口（只有方法签名，没有 Spring 注解），基础设施层提供
`UserRepositoryAdapter` 实现它。适配器里我看到两件值得记的事：

一是**邮箱的双写**。`save()` 同时写了 `emailCipher` 和 `emailHash`：

```java
e.setEmailCipher(encryptor.encrypt(user.email()));   // AES-256-GCM，可解密还原
e.setEmailHash(encryptor.digest(user.email()));      // HMAC-SHA256，不可逆但可精确查找
```

`FieldEncryptor` 用了两套密钥材料：`AES/GCM/NoPadding`（12 字节随机 IV，128 位 tag）负责加密，
`HmacSHA256` 负责生成确定性摘要。摘要不可逆，但**同样的输入永远得到同样的摘要**，
所以 `existsByEmail` 可以直接拿摘要去查数据库做唯一性约束。加密解决"看得见"，摘要解决"查得到"，
两者一起才同时满足可还原与可检索。

二是**计数器不走聚合**。ADR-008 明确写了"计数器类字段（分数、回答数、浏览数）不由聚合回写，
而由原子 UPDATE 维护，避免读-改-写覆盖并发增量"。这解释了为什么 `User` 里有 `version` 字段
（乐观锁版本号）但适配器里没有直接 set 它——版本号由 JPA 自己在 `save` 时搬运。

### 3. 应用层做用例编排，且不依赖 Spring Security

应用层的 `UserRegistrationService.register` 顺序很清楚：
`PasswordPolicy.validate` → `User.register` → `ensureUnique`（三次存在性检查）→ `users.save`
→ `events.publish(new UserRegisteredEvent(...))` → `audit.record(...)`。

值得注意的是**身份是怎么传进来的**。共享内核的 `Actor` 是一个 record：

```java
public record Actor(long userId, String displayName, Role role) implements Serializable
```

它由**接口层**从安全上下文解析后**显式传入**应用服务。这样做的直接后果是：应用层和领域层都不 import
Spring Security，单元测试可以随便 `new Actor(1L, "x", Role.ADMIN)` 造任意身份。
我认为这是整个参考实现里最优雅的一处设计——把"谁在操作"变成一个普通的值对象，
领域层就彻底不需要知道认证框架的存在。

`IdentityApiImpl` 则是**开放主机服务（OHS）**的实现：把 `User` 翻译成 `UserSummary`，
对外只暴露 `identity-api` 模块。它的 `canManageCourse` 体现了"权限判断放在应用层"：
管理员直接放行，其他角色查 `CourseMember.role().canManage()`。

### 4. 事件发布与 ADR-002 呼应

`register` 里那句 `events.publish(new UserRegisteredEvent(...))` 就是 ADR-002 事务性发件箱的入口。
共享内核里的 `IntegrationEventPublisher`、`IntegrationEvent`、`EventIds`、`ProcessedEventStore`
四个接口构成了跨上下文协作的最小契约集。`EventIds.next()` 保证事件 ID 全局唯一——
这也是 ADR-004 声誉账本"唯一键 `(event_id, user_id, reason)` 天然幂等"的前提。

### 5. 架构约束是被 CI 强制的，不是靠自觉

`ArchitectureTest` 用 ArchUnit 把 ADR-001 和 ADR-008 写成了 6 条可执行规则（FF-1 ~ FF-6）：

| 规则 | 约束 |
| --- | --- |
| FF-1 | 领域层不得依赖 Spring / JPA / Hibernate / Jackson |
| FF-2 | 跨上下文只能经由对方的 `api` 包（发布语言） |
| FF-3 | 四个上下文之间不允许循环依赖 |
| FF-4 | 六边形分层方向：依赖只能由外向内 |
| FF-5 | `api` 包只能依赖 JDK、共享内核和其他 `api` 包 |
| FF-6 | 每个上下文的表必须带自己的前缀（`id_` / `qa_` / `rep_` / `dis_`） |

FF-6 的实现方式很有意思——它不是简单断言注解值，而是写了一个自定义 `ArchCondition`，
运行时根据实体所在包反查应使用的前缀，再检查 `@Table(name=...)` 是否匹配。
这意味着**即使有人新写了一个实体忘了加前缀，CI 会当场拦下**。

我理解这就是 arc42 第 10 章"架构适应度函数"的真正含义：把架构文档里的"应该"翻译成 CI 里的"必须"。

## 二、8 条 ADR 各自解决了什么问题

| ADR | 决策 | 解决的核心问题 |
| --- | --- | --- |
| 001 | 模块化单体 + 六边形分层 | 5 人 16 周无运维，四个子域共享同一套用户与数据 → 必须单一量子；选模块化单体而非微服务（微服务加权评分最低 96/160） |
| 002 | 事务性发件箱 | "采纳回答"要触发 3 个下游，同步调用会放大失败面，异步发事件会丢 → 业务写入与 `outbox_event` 同事务提交，至少一次投递 + 消费端幂等 |
| 003 | Redis 服务端会话而非 JWT | 教师要**立即**封禁账号；JWT 无法即时失效，且 localStorage 里的令牌遇 XSS 即被窃 → 封禁即删会话，Cookie 设 `HttpOnly` + `SameSite=Lax`，登录后轮换会话 ID |
| 004 | 声誉只追加账本 + 定期对账 | `UPDATE users SET reputation = reputation + 15` 回答不了"这 15 分从哪来" → 只追加 `rep_ledger`，汇总值是派生量，每日对账用 `co_reputation_mismatches` 指标暴露 |
| 005 | 中文全文检索 | 中文分词与 `LIKE` 效率/准确性都不可接受 → 走专用全文索引（课程预留） |
| 006 | 用户内容一律软删除 | 回答引用问题、评论引用回答、声誉流水引用回答，物理删除会造成悬挂引用 → `deleted_at` 标记，所有查询显式带 `deleted_at IS NULL` |
| 007 | 前后端以 OpenAPI 契约协作 | 5 人要前后端并行，口头约定接口会在联调期集中返工 → springdoc 生成契约 + RFC 9457 Problem Details + 统一分页 `{items,total,page,size}`，改接口先改契约 |
| 008 | 领域对象与 JPA 实体分离 | 聚合直接标 `@Entity` 会被"无参构造 + 可变字段 + 延迟加载代理"绑架 → 领域层纯 Java，基础设施层手写映射，代价是每个聚合约 40 行样板 |

### 我自己最受启发的三条

**ADR-001 的"被否决方案"写法。** 三条备选方案都给了加权评分（微服务 96/160、分层单体 87/160、
基于服务 110/160）。评分最高的那个（基于服务 110 分）被否决了，理由写得很清楚：
"其优点（边界清晰）已被模块化边界获得"。**这说明选型不是选最高分，是选"收益/成本比"最高的**。
微服务分数低不是因为它不好，是因为我们没有独立伸缩、没有独立部署、没有运维人员——
这三个"没有"决定了它是过度工程。

**ADR-004 的"可解释性优先于性能"。** 声誉账本一次动作要写两张表（账本 + 汇总），是典型的写放大，
被明确列为缺点。ADR 的取舍标准是：**能回答"这 15 分从哪来"比省一次 UPDATE 更重要**。
如果我在做别的系统，很可能就直接 UPDATE 了。

**ADR-006 的"显式代价"写法。** 每条 ADR 都有"负面"一节，不藏代价。ADR-006 老实写"所有查询都必须显式带
`deleted_at IS NULL`"——这是一个真实的、会长期增加维护成本的负担。**写 ADR 不写负面部分，
就等于没有做决策，只是做了一份说明。**

## 三、我打算怎么用这些结论（作为 DV1 的行动项）

1. **开发任何 Discovery 代码前，先看 `ArchitectureTest` 的 FF-2 和 FF-5**。
   跨上下文引用 `co-identity` 时只能用 `com.campusoverflow.identity.api` 里的类，
   不能直接引 `identity.domain.User`。这一条我最容易违反，因为直觉上"用领域对象更方便"。
2. **Discovery 的事件消费必须幂等**，对齐 ADR-002 的"至少一次"语义：
   用 `ProcessedEventStore` 做去重，理由和 ADR-004 的唯一键思路一致。
3. **计数类字段（通知未读数、搜索命中数）不回写聚合**，用原子 UPDATE，对齐 ADR-008。
4. **每写完一个 Discovery 类就跑一次 `mvn test -pl co-bootstrap -Dtest=ArchitectureTest`**，
   不要等到提 PR 才发现违反了 FF 规则——那是"允许红"的 `ci.yml` 之外的第二道门。
5. **测试方面**：`ci.yml` 现在是红的（38 个 TODO 测试未实现），这是**需求清单而非环境问题**。
   我的职责是保证 `skeleton-check` 永远绿，并让全量测试的红**数量单调递减**，
   而不是去改断言把红变绿——那是学术不端。

## 四、还没想清楚的问题（留给团队一起讨论）

- **模块化单体的"物理隔离不足"风险怎么持续压制？** ADR-001 自己承认开发者可以绕过规则，
  靠 FF-1~FF-6 自动化检查兜底。但 ArchUnit 只能检查**已存在的依赖**，
  检查不了"新增了不该有的耦合"这种意图性破坏（比如为了让某个功能跑通而临时引一个跨上下文的类）。
  是否需要 CODEOWNERS 对 `backend/co-discovery/` 强制指定 reviewer？
- **Discovery 作为"第一拆分候选"，什么时候拆？** ADR-001 说它是纯下游、只读投影、无强一致要求，
  确实最适合拆。但现在只有 16 周，拆了会分散精力。是否应该定一个明确的"不拆"信号，
  比如"全量测试全绿 + 覆盖率达标"再讨论？
- **ADR-002 的"最终一致"在演示时怎么解释？** 采纳回答后声誉有数百毫秒延迟，
  评委现场点击会看到延迟。是加一个 loading 提示更好，还是在演示脚本里提前说明？
